## 1. Що зроблено за тиждень

### 1.1. Завдання 0: Прибирання і контроль диска
- **Гілка:** Створено гілку `feature/week3-backend`.
- **Розбіжність лічильників датасету:** З'ясовано точну причину початкової невідповідності (602/202/202 vs 600/200/200). Команда підрахунку `find <dir> | wc -l` (без прапорця `-type f`) повертала кореневий каталог кожної з 7 директорій датасету як перший рядок виводу (+1 на кожну папку). Фактична кількість валідних зображень у датасеті становить рівно **6000**:
  - `train`: 169 healthy / 431 sick (разом 600)
  - `val`: 58 healthy / 142 sick (разом 200)
  - `test`: 54 healthy / 146 sick (разом 200)
  - `unlabeled`: 5000 images
- **Маніфест нерозмічених даних:** Згенеровано файл [`ml/data/unlabeled_manifest.csv`](../../ml/data/unlabeled_manifest.csv) на 5000 рядків із хешами SHA-256 та pHash. Для точного дубліката `unlabeled__7__1.jpg` (ідентичний до `train__25.jpg`) встановлено прапорець `exclude=1`.
- **Контроль диска:** Кеш `pip` та SDK налаштовано на D:, віртуальний диск Docker WSL розташований на D:. На диску C: звільнено понад 14 ГБ.

### 1.2. Завдання 1: Контракт API
- Розроблено та зафіксовано повний контракт у [`docs/api.md`](../../docs/api.md) з ендпоінтами `/health`, `/model-info`, `/predict`, `/feedback` та уніфікованою схемою обробки помилок.

### 1.3. Завдання 2: Сервіс інференсу
- Створено модульну структуру `backend/app/` із розділенням на шари:
  - `routers/` — валідація запитів, HTTP-коди.
  - `services/` — бізнес-логіка, неблокуючий інференс моделі у пулі потоків (`asyncio.to_thread`), генерація теплових карт.
  - `repositories/` — доступ до БД через SQLAlchemy 2.0.
  - `models/` — ORM-моделі `Prediction` та `Feedback`.
  - `schemas/` — Pydantic v2 схеми валідації.
- Винесено спільну попередню обробку зображень у [`shared/transforms.py`](../../shared/transforms.py), що гарантує 100% ідентичність пайплайнів у `ml/src/dataset.py` та API (resize 1.14x, center crop 224x224, нормалізація ImageNet).
- **Верифікація:** Тест [`backend/tests/verify_val_10.py`](../tests/verify_val_10.py) на 10 випадкових валідаційних фото підтвердив **нульову розбіжність (`0.0000`)** передбачених міток та ймовірностей між API та навчальним скриптом `evaluate.py`.

## 2. Команди запуску

### Запуск через Docker Compose (рекомендований для продакшну):
```bash
docker compose up --build -d
# Перевірка:
curl http://localhost:8000/health
# Адмінка:
http://localhost:8000/admin
```

### Локальний запуск (режим розробки з локальним SQLite):
```bash
# 1. Запуск міграцій:
cd backend && alembic upgrade head && cd ..
# 2. Запуск сервера:
uvicorn backend.app.main:app --host 0.0.0.0 --port 8000 --reload
```

### Запуск мобільного застосунку Flutter:
```bash
cd mobile
# Прокидання порту для підключеного по USB Android-пристрою:
adb reverse tcp:8000 tcp:8000
flutter run
```

## 3. Час відповіді інференсу (CPU та GPU)

Заміри проведено на тестових зображеннях (середнє за 15 прогонів після прогріву):

| Режим / Пристрій | Без Grad-CAM (мс) | З Grad-CAM (мс) | Накладні витрати на інтерпретацію |
|---|---|---|---|
| **CPU (AMD/Intel)** | **29.79 мс** | **135.84 мс** | +106.05 мс (~4.6x) |
| **GPU (NVIDIA CUDA)** | **5.65 мс** | **31.91 мс** | +26.26 мс (~5.7x) |

*Висновок:* Генерація Grad-CAM додає зворотний прохід градієнтів по згортковому блоку та операцію інтерполяції з накладенням кольорів. Навіть на CPU загальний час відповіді (<140 мс) є комфортним для мобільного користувача в режимі реального часу.

## 4. Оцінка розміру Docker-образу

- Завдяки використанню збірки `torch/torchvision` із репозиторію CPU-коліс (`https://download.pytorch.org/whl/cpu`), розмір шару PyTorch зменшено з **~2.8 ГБ** (версія CUDA) до **~170 МБ**.
- Очікуваний підсумковий розмір образу `plant-disease-api` становить **~450–550 МБ**, що вкладається в жорсткі вимоги щодо економії дискового простору.

## 5. Спостереження з Grad-CAM

Аналіз проведено на сітці з 16 зображень вибірки `test` ([`ml/reports/gradcam_grid_16.png`](../../ml/reports/gradcam_grid_16.png)):
1. **Зони ураження (`sick`):** Нейромережа демонструє точне локальне фокусування на крапкових некрозах, бурих краях листя та зонах ураження. Фокусування на фоні відсутнє, якщо листок чітко відокремлений від оточення.
2. **Здорові листки (`healthy`):** Теплова пляма розподілена рівномірно вздовж судинної сітки листка (структурний патерн), що підтверджує сприйняття здорової поверхні в цілому.
3. **Хибні спрацьовування:** У випадках помилкових передбачень виявлено, що модель реагує на світлові відблиски (сонце/спалах) на гладких поверхнях або темні тіні по кутах кадру. Це підтверджує необхідність аугментації `ColorJitter` та показу карти уваги користувачу в застосунку.

## 6. Відомі обмеження

1. **Фізичний Android-пристрій:** На момент запуску команди `adb devices` фізичний телефон не був підключений через USB-кабель з увімкненим USB Debugging. Для перевірки на телефоні користувачу достатньо під'єднати апарат і виконати `adb reverse tcp:8000 tcp:8000` та `flutter run`.
2. **Розмір завантажуваного файлу:** Встановлено ліміт 10 МБ. Файли більшого розміру відхиляються зі статусом `413 FILE_TOO_LARGE`.
